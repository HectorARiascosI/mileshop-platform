# Plan objetivo de versión 1.0.0 — MileShop Platform

## 1. Propósito

Este documento define el horizonte operativo y técnico para la primera versión estable de MileShop Platform. La intención no es seguir experimentando sin criterio, sino cerrar una entrega reproducible, verificable, documentada y preparada para operación real.

La versión 1.0.0 se alcanzará solo cuando se cumpla el Definition of Done completo de este plan, incluyendo validación técnica, validación de negocio, pruebas automáticas, entorno reproducible y evidencia de despliegue y rollback.

## 2. Principios del plan

- la entrega tiene alcance fijo y medible;
- cada dominio tiene propietario claro;
- no hay cambios directos a `main` sin release controlada;
- cada milestone tiene criterios de aceptación y evidencia;
- no se etiqueta una versión sin pasar las pruebas requeridas;
- la documentación refleja el estado real del sistema;
- cualquier riesgo operativo debe tener plan de mitigación y rollback.

## 3. Alcance objetivo de la v1

La primera versión de MileShop Platform debe incluir, como mínimo:

### 3.1 Frontend
- catálogo público con productos reales;
- flujo de agregar/quitar productos del carrito;
- vista de checkout y resumen de pedido;
- confirmación de compra con feedback claro al usuario;
- comportamiento funcional y responsivo en entorno real.

### 3.2 Backend y servicios
- gateway público con health checks;
- servicio de catálogo con datos reales y versionados;
- servicio de órdenes con validaciones de dominio;
- worker de notificaciones con idempotencia y deduplicación;
- contratos de eventos y APIs con versionado explícito.

### 3.3 Datos y persistencia
- PostgreSQL por servicio cuando aplique;
- migraciones reproducibles;
- datos semilla realistas para desarrollo;
- estado definido para entorno local y preproducción.

### 3.4 Operación
- scripts reproducibles para levantar el stack local;
- health checks operativos;
- procedimientos de diagnóstico y rollback;
- documentación clara para mantenimiento y despliegue.

## 4. Milestones del plan

### Milestone 1 — Base técnica y gobernanza
Objetivo: dejar el repositorio estable y profesional.

Criterios:
- estructura del monorepo clara y documentada;
- política de ramas y PR definida;
- CI con validación real;
- documentación base del repo disponible;
- procedimientos de seguridad y secreto definidos.

Evidencia:
- `main` protegida;
- `develop` funcional;
- PRs con evidencia y checks;
- historial de ramas consistente.

### Milestone 2 — Catalog, storefront y experiencia base
Objetivo: dejar la compra por catálogo funcionando con UX real.

Criterios:
- catálogo disponible por API;
- storefront con flujo de compra completo;
- estado resiliente ante errores de servicio;
- validación del flujo principal en local.

Evidencia:
- pruebas de catálogo;
- pruebas de gateway;
- smoke test del flujo storefront → checkout.

### Milestone 3 — Órdenes y dominio transaccional
Objetivo: cerrar la lógica de negocio principal del pedido.

Criterios:
- validación estricta de líneas y totales;
- persistencia de ordenes por servicio;
- creación de payload de evento con esquema versionado;
- pruebas unitarias y de integración del dominio.

Evidencia:
- pruebas del servicio de órdenes;
- validación de event payloads;
- comprobación del flujo de creación de pedido.

### Milestone 4 — Notificaciones e integración
Objetivo: entregar la parte operativa del sistema con eventos y observabilidad.

Criterios:
- notificaciones disparadas solo una vez con deduplicación;
- manejo de reintentos y idempotencia;
- logs y fallbacks definidos;
- pruebas de worker y contract test de evento.

Evidencia:
- pruebas de deduplicación;
- validación de envío de eventos;
- verificación de comportamiento ante retries.

### Milestone 5 — QA técnica completa y entorno preproducción
Objetivo: validar que todo el sistema funciona como un conjunto coherente.

Criterios:
- ejecución completa de `typecheck`, `lint`, `test`, `build`;
- validación de `docker compose` y entorno local reproducible;
- pruebas de integración entre services y frontend;
- configuración de variables de entorno documentada;
- no quedan errores críticos ni warnings altos de seguridad.

Evidencia:
- CI verde en branch de release;
- stack local operativo;
- smoke tests del sistema completo;
- auditoría de seguridad y dependencias.

### Milestone 6 — Release v1.0.0
Objetivo: congelar la primera versión estable y documentada.

Criterios:
- milestone 5 cumplido;
- tag final creado;
- evidencia de release guardada;
- rollback y operación documentados;
- README y documentación del proyecto en estado final.

Evidencia:
- release branch creada y validada;
- versionado semántico aplicado;
- tag `v1.0.0` publicado;
- changelog y notas de versión documentadas.

## 5. Definition of Done de la v1

La primera versión se considera entregada solo cuando se cumplen todos estos puntos:

### 5.1 Calidad de código
- typecheck en frontend y servicios pasa;
- lint pasa;
- tests unitarios pasan;
- tests de integración relevantes pasan;
- build del monorepo pasa;
- no hay fallos críticos de compilación.

### 5.2 Ambiente y despliegue
- entorno local reproducible con instrucciones claras;
- servicios arrancan con configuración correcta;
- health checks responden correctamente;
- compose y scripts de operación validados.

### 5.3 Reglas de negocio
- catálogo funcional;
- carrito funcional;
- checkout funcional;
- orden creada y validada;
- notificación disparada con consistencia.

### 5.4 Operación y soporte
- rollback documentado;
- diagnósticos definidos;
- procedimientos operativos disponibles;
- observabilidad mínima funcionando;
- ownership de cada dominio explicitado.

### 5.5 Documentación
- README actualizado con objetivo del proyecto;
- workflows documentados;
- release playbook disponible;
- plan de v1 registrado en repositorio;
- decisiones de arquitectura documentadas en ADR.

## 6. Criterios de release

Una versión solo puede etiquetarse cuando suceden estas condiciones:

1. `develop` está estable y validada.
2. una `release/<version>` existe y pasa la validación final.
3. el sistema completo funciona en entorno local y preproducción.
4. tests automáticos pasan con evidencia en CI.
5. no quedan defectos críticos abiertos.
6. la documentación de operación está actualizada.
7. existe rollback o reversión definida.
8. la versión se etiqueta con semver: `vX.Y.Z`.

## 7. Política de versionado

Se usará versionado semántico:

- `MAJOR`: cambios incompatibles o renovación funcional principal;
- `MINOR`: nuevas funcionalidades y mejoras compatibles;
- `PATCH`: correcciones y ajustes menores.

La primera entrega oficial será:

- `v1.0.0`

Solo se crea después de cumplir el Definition of Done completo.

## 8. Flujo operativo recomendado

```bash
git checkout develop
git pull --ff-only origin develop
git checkout -b release/2026.09.13
# ejecutar validaciones finales
npm run typecheck
npm run lint
npm run test
npm run build
# checks de entorno y smoke tests
# si todo pasa
git checkout main
git merge --no-ff release/2026.09.13
git tag -a v1.0.0 -m "release: v1.0.0"
git push origin main --tags
```

## 9. Conclusión

La primera versión no es “lo que ya funciona en local”, sino lo que ha pasado la validación completa, la operación controlada y la documentación profesional. Este plan da un horizonte claro para la entrega real y evita el estado de experimentación sin dirección.

La versión 1.0.0 será la primera marca formal del proyecto y no se creará antes de cumplir todas las decisiones y pruebas de este documento.
